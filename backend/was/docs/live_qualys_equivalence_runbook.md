# Live Qualys Production Validation Runbook

## Purpose

Use this runbook to validate the production WAS report pipeline with approved
nonproduction Qualys data. The container executes only code installed from
`src/was_reports` and `src/was_mailer`. The historical source directories are
not copied into the image and are not part of this procedure.

Compare the generated report with an approved baseline report when one is
available. The baseline may be a previously approved report, but it must be
supplied independently and must not be generated by executing historical code.

## Security Rules

- Use only approved nonproduction Qualys credentials and stakeholder tags.
- Do not place Qualys or report passwords in commands, logs, tickets, or Git.
- Do not run `source .env`. Pass `.env` to Docker with `--env-file`.
- Disable shell command tracing with `set +x` before handling credentials.
- Do not generate an unencrypted report.
- Do not use `--create-missing-password` unless password creation is an
  intentional part of the approved test.
- Keep reports and logs private and remove them according to the approved
  retention policy.
- Use `--dry-run-email` for scheduled batches until content and recipients are
  verified. For on-demand testing, generate/archive without `--send-email`
  first, or explicitly approve one real test email as described below.

## Preconditions

Confirm all of the following before starting:

- The branch and commit are approved for nonproduction validation.
- `backend/was/.env` contains approved database, Qualys, S3, and SES settings.
- `.env` permissions restrict access to the operator.
- The Postgres stakeholder row exists and has a report password.
- The Qualys stakeholder tag exists and has representative scan data.
- The EC2 instance role can access the configured S3 prefix.
- The instance role can assume `WAS_SES_ROLE_ARN`, which permits
  `ses:SendRawEmail` for the approved sender; no named profile is needed.
- Docker is running and the production image has been rebuilt from the current
  source.

## Build And Verify The Image

Run these commands from `backend/was`:

```bash
set +x
set -o pipefail

test -f .env
make build

docker run --rm --entrypoint sh was-reporting -c '
  test ! -e /app/was_report
  test ! -e /app/update_tracker
  test -d /app/src/was_reports
  test -d /app/src/was_mailer
'
```

The filesystem check must exit with status `0`. A nonzero status means the
image does not meet the production-only boundary.

## Generate One Local Report

Use a private, timestamped host directory so a prior report is not overwritten:

```bash
export WAS_VALIDATION_TAG="REPLACE_WITH_APPROVED_NONPRODUCTION_TAG"
export WAS_VALIDATION_RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)"
export WAS_VALIDATION_ROOT="$(pwd)/local-output/validation/${WAS_VALIDATION_RUN_ID}"

mkdir -p "${WAS_VALIDATION_ROOT}"
chmod 700 "${WAS_VALIDATION_ROOT}"

set +e
docker run --rm \
  --env-file .env \
  --user "$(id -u):$(id -g)" \
  -v "${WAS_VALIDATION_ROOT}:/output" \
  was-reporting \
  was-reports \
  --tag "${WAS_VALIDATION_TAG}" \
  2>&1 | tee "${WAS_VALIDATION_ROOT}/generation.log"
export WAS_VALIDATION_STATUS="${PIPESTATUS[0]}"
set -e

test "${WAS_VALIDATION_STATUS}" -eq 0
find "${WAS_VALIDATION_ROOT}" -maxdepth 1 -type f -name '*.pdf' -print
```

The generated PDF must be encrypted with the stakeholder password stored in
Postgres. Review the log for retries, unexpected tracebacks, and sensitive
values before retaining or sharing it.

## Full On-Demand Functional Test On EC2

This test performs live Qualys calls, creates one new run, uploads an encrypted
PDF, downloads that S3 object through the mailer, and sends one actual email.
It does not depend on a recent-scan candidate or reuse a missing historical PDF.
Approve the recipient and tag before running. From `backend/was`:

```bash
set +x
umask 077
mkdir -p local-output/e2e
RUN_STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
make on-demand-report TAG="CROSSFEED" SEND_EMAIL=1 \
  TEST_RECIPIENTS="craig.duhn@associates.cisa.dhs.gov" \
  2>&1 | tee "local-output/e2e/on-demand-${RUN_STAMP}.log"
RUN_STATUS=${PIPESTATUS[0]}
printf 'Functional test exit code: %s\n' "$RUN_STATUS"
```

This is a standalone report test: it creates a report-run record but does not
invent or change a daily tracker row. To validate tracker delivery, first select
an actual matching unsent row without an existing report run, then explicitly
pass its ID as `TRACKER_ID`. A test-recipient send marks that linked row sent;
do not use an operational row that must still be sent to customer recipients.

Using the new run ID printed in the log, query the WAS database:

```sql
SELECT id, stakeholder_tag, status, output_path, source_tracker_id,
       email_status, emailed_at, email_message_id, email_error
FROM public.was_report_runs
WHERE id = NEW_RUN_ID;
```

Replace `NEW_RUN_ID` with the numeric ID. Expect `completed`, an S3 reference,
`sent`, and populated acceptance timestamp/message ID. If a real tracker was
linked, verify that row separately:

```sql
SELECT tracker.id, tracker.tag, tracker.report_sent_date
FROM public.was_daily_report_tracker AS tracker
JOIN public.was_report_runs AS runs ON runs.source_tracker_id = tracker.id
WHERE runs.id = NEW_RUN_ID;
```

For standalone runs, zero tracker rows is expected, not a failure. Copy the
exact object key from `output_path`, omitting `s3://cisa-was-reports/`:

```bash
aws s3api head-object --bucket cisa-was-reports --key "EXACT_OBJECT_KEY"
```

The object must exist and have nonzero size. Verify its encryption metadata
against bucket requirements, then confirm inbox receipt and open the attached
PDF using the stakeholder password obtained through approved secure access.
Review that unsupported sensitive-finding data is labelled unavailable, not
zero. Record the source commit, run ID, S3 reference, message ID, and recipient
confirmation, but never record the report password.

For an email failure, the PDF remains archived and the on-demand run remains
held for explicit delivery. Use `was-mailer --report-run-id` with the approved
recipient override to retry, not a new generation command. For failed upload,
there must be no successful completion or SES acceptance. If S3 succeeded but
the completion write failed, preserve the artifact and reconcile the run. If
SES accepted but the database update failed, verify delivery before retrying:
exactly-once delivery across SES and Postgres is not guaranteed.

## Compare With An Approved Baseline

Copy an approved encrypted baseline PDF into a separate private directory.
Read the comparison password without echoing it and pass only the environment
variable name to Docker:

```bash
export WAS_BASELINE_PDF="/absolute/private/path/to/approved-baseline.pdf"
export WAS_GENERATED_PDF="$(find "${WAS_VALIDATION_ROOT}" \
  -maxdepth 1 -type f -name '*.pdf' -print -quit)"

read -s -p "Report comparison password: " WAS_REPORT_COMPARISON_PASSWORD
printf '\n'
export WAS_REPORT_COMPARISON_PASSWORD

docker run --rm \
  --env WAS_REPORT_COMPARISON_PASSWORD \
  -v "${WAS_BASELINE_PDF}:/reports/baseline.pdf:ro" \
  -v "${WAS_GENERATED_PDF}:/reports/generated.pdf:ro" \
  --entrypoint was-compare-reports \
  was-reporting \
  /reports/baseline.pdf \
  /reports/generated.pdf \
  | tee "${WAS_VALIDATION_ROOT}/comparison.json"

unset WAS_REPORT_COMPARISON_PASSWORD
```

The comparator checks encryption, page count, page dimensions, normalized page
text, attachments, and selected metadata. A difference is not automatically a
defect because report dates and live Qualys data can change. Document and
review every difference before approval.

## Validate S3 Without Sending Email

Run one controlled recent-scan batch with email disabled:

```bash
docker run --rm \
  --env-file .env \
  was-reporting \
  --recent-scans \
  --tag "${WAS_VALIDATION_TAG}" \
  --skip-tracker-refresh \
  --limit 1
```

Verify the resulting `was_report_runs.output_path` is an S3 URI and confirm the
object exists with `aws s3api head-object`. Do not use this step when the
selected tracker row has already been claimed or delivered.

## Validate Email Delivery

After report and S3 validation, send only to an approved test recipient:

```bash
docker run --rm \
  --env-file .env \
  was-reporting \
  --recent-scans \
  --tag "${WAS_VALIDATION_TAG}" \
  --skip-tracker-refresh \
  --send-email \
  --test-recipients "REPLACE_WITH_APPROVED_TEST_RECIPIENT" \
  --limit 1
```

Confirm all three records of success:

1. The command exits with status `0`.
2. SES returns a message ID that is stored on `was_report_runs`.
3. The approved recipient receives and opens the encrypted report.

## Acceptance Criteria

A production validation passes only when:

- The image contains no historical runtime directories.
- Report generation exits successfully.
- The expected encrypted PDF opens with the stored stakeholder password.
- Required report pages, charts, and attachments are present.
- Expected unsupported Qualys module responses are logged and skipped only by
  the approved conditional handling.
- Temporary Qualys reports are deleted after success and failure paths.
- S3 storage succeeds under the configured run-specific key.
- Email delivery, when tested, is accepted by SES, persisted in Postgres, and
  confirmed by the recipient.
- Logs contain no credentials, report passwords, or unintended report data.
- The commit SHA, image ID, tag, date, operator, and result are recorded in the
  approved validation record.

## Cleanup

```bash
unset WAS_VALIDATION_TAG
unset WAS_VALIDATION_RUN_ID
unset WAS_VALIDATION_ROOT
unset WAS_VALIDATION_STATUS
unset WAS_BASELINE_PDF
unset WAS_GENERATED_PDF
```

Remove the validation directory only when allowed by the approved retention
and evidence-handling process. Never commit generated reports, logs,
comparison output, checksums, or `.env`.
